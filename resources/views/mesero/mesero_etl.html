ETL — Extract, Transform, Load

Antes de que el sistema pueda segmentar mesas o entrenar modelos, los datos de las comandas deben pasar por un proceso de extracción, transformación y carga. Este documento explica exactamente qué pasa con los datos desde que se guardan en MongoDB hasta que se convierten en los clusters que ves en el dashboard.

Contexto

¿ETL o ELT? — Por qué este proyecto usa ETL

✓ ETL (este proyecto)

Los datos se extraen de MongoDB con filtros aplicados desde el inicio, se transforman en memoria (normalización, clustering, modelado) y el resultado se carga directamente al cliente como JSON. Nunca se persiste el resultado intermedio en ninguna base de datos.

Flujo: MongoDB → RAM (NumPy) → JSON al navegador

✗ ELT (no aplica aquí)

En ELT los datos crudos se cargan primero a un data warehouse (como BigQuery o Snowflake) y la transformación ocurre dentro del almacén con SQL o Spark. Requiere infraestructura de datos dedicada que no existe en este proyecto.

Flujo ELT: Fuente → Data Warehouse → Transform con SQL/Spark
Clave: el ETL de este proyecto es online y stateless — se recalcula completamente en cada petición a /api/mesero/kmeans, usando siempre los últimos 90 días de comandas.

E — Extract

Extracción de datos desde MongoDB

La extracción lee la colección comandas y aplica tres filtros simultáneos: por mesero, por estado y por ventana de tiempo. Solo entran al pipeline los servicios completamente cerrados de los últimos 90 días.

Filtro 1 — Mesero

Solo comandas del mesero autenticado en la sesión actual. Cada mesero ve exclusivamente sus propias mesas.

"mesero_id": mesero_oid
Filtro 2 — Estado

Solo comandas finalizadas. Las abiertas o canceladas no representan un ingreso real y distorsionarían el análisis.

"estado": {"$in": ["pagada", "cerrada"]}
Filtro 3 — Ventana

Solo los últimos 90 días. Ventana deslizante: siempre refleja el comportamiento reciente, ignorando datos históricos muy antiguos.

"fecha_cierre": {"$gte": hace_90_dias}
Código de extracción
services/mesero_kmeans_service.py · línea 38
# Calcular ventana de 90 días desde hoy
hace_n_dias = datetime.now() - timedelta(days=90)
mesero_oid = ObjectId(mesero_id)

# Pipeline de extracción + pre-agrupación en MongoDB
pipeline = [
  { "$match": {
    "mesero_id": mesero_oid,
    "estado": { "$in": ["pagada", "cerrada"] },
    "fecha_cierre": { "$gte": hace_n_dias }
  } },
  { "$group": {
    "_id": "$mesa_numero",
    "num_visitas": { "$sum": 1 },
    "ticket_promedio": { "$avg": "$total" },
    "ticket_std": { "$stdDevPop": "$total" },
    "ingreso_total": { "$sum": "$total" },
    "propina_promedio":{ "$avg": "$propina" }
  } },
  { "$match": { "num_visitas": { "$gte": 1 } } },
  { "$sort": { "ingreso_total": -1 } }
]

# Ejecutar y cargar en memoria
mesas_raw = list(db.comandas.aggregate(pipeline))
El $group colapsa N comandas de la misma mesa en 1 fila — la extracción ya llega pre-agrupada por mesa, no en bruto comanda a comanda. Esto reduce el volumen de datos que pasa a la fase de transformación.
Guardia de datos mínimos — K-Means requiere al menos 3 mesas
services/mesero_kmeans_service.py · línea 63
if len(mesas_raw) < 3:
  return {
    "puntos": [],
    "aviso": "Se necesitan al menos 3 mesas con historial para segmentar."
  }
Si el mesero tiene menos de 3 mesas con comandas en la ventana de 90 días, el pipeline se interrumpe aquí — K-Means no puede crear 3 clusters con menos de 3 puntos.

T — Transform

Transformación en memoria — 5 pasos

Los documentos MongoDB no pueden entrar directamente al modelo de Machine Learning. Deben pasar por cinco transformaciones que los convierten en matrices numéricas listas para scikit-learn.

T1 Conversión de formato — de documentos BSON a matrices NumPy
services/mesero_kmeans_service.py · línea 69
# Entrada: lista de dicts MongoDB (BSON)
# mesas_raw = [{"_id": 3, "num_visitas": 45, "ticket_promedio": 162.5, ...}]

# Matriz para K-Means → shape (n_mesas, 2)
X_kmeans = np.array([
  [ float(m["num_visitas"]), float(m["ticket_promedio"]) ]
  for m in mesas_raw
])

# Matriz para Random Forest → shape (n_mesas, 3)
X_arbol = np.array([
  [ float(m["num_visitas"]),
    float(m["ticket_promedio"]),
    float(m.get("ticket_std") or 0) ] # None → 0
  for m in mesas_raw
])
El float() explícito evita errores de tipo con Decimal128 de MongoDB que NumPy no acepta directamente. K-Means usa 2 features (visualizables en scatter), el RF usa 3 (agrega variabilidad del ticket).
T2 Manejo de valores nulos — $stdDevPop devuelve null cuando solo hay 1 comanda
services/mesero_kmeans_service.py · línea 80
# Problema: si una mesa tiene exactamente 1 comanda,
# $stdDevPop devuelve None (no se puede calcular desviación de 1 valor)

# Solución: reemplazar None con 0 (variabilidad nula = ticket constante)
float(m.get("ticket_std") or 0)

# El "or 0" cubre dos casos:
# m.get("ticket_std") → None (mesa con 1 comanda) → 0
# m.get("ticket_std") → 0.0 (todas iguales) → 0
Una mesa con variabilidad 0 significa que siempre genera el mismo ticket — comportamiento predecible. Es un dato válido, no un error a eliminar.
T3 Normalización — StandardScaler — igualar escalas entre frecuencia y ticket
services/mesero_kmeans_service.py · línea 85
# Sin normalización: ticket (ej. 350 MXN) dominaría sobre
# frecuencia (ej. 8 visitas) solo por ser un número más grande

scaler = StandardScaler()
X_scaled = scaler.fit_transform(X_kmeans)

# Antes: Frecuencia ∈ [2..80], Ticket ∈ [120..480]
# Después: ambas variables ∈ [-2..+2] aprox. (media=0, std=1)

# ⚠ Solo para K-Means — el Random Forest NO necesita normalización
# (los árboles de decisión son scale-invariant)
Z-score: cada valor se transforma en (valor − media) / desviación_estándar. El scaler se guarda en memoria para poder hacer inverse_transform después y recuperar los centroides en las unidades originales.
T4 Clustering — K-Means — asignar cada mesa a un segmento
services/mesero_kmeans_service.py · línea 88
k = min(3, len(mesas_raw)) # k=3, o menos si hay pocas mesas
km = KMeans(n_clusters=k, random_state=42, n_init=10)
km.fit(X_scaled)

# Reordenar clusters para que 0=VIP, 1=Regular, 2=Ocasional
# (K-Means asigna IDs aleatorios en cada ejecución)
centroids_orig = scaler.inverse_transform(km.cluster_centers_)
orden = np.argsort(centroids_orig[:, 0] + centroids_orig[:, 1])[::-1]
remap = { old: new for new, old in enumerate(orden) }
labels_remap = np.array([remap[l] for l in km.labels_])
El reordenamiento ordena los centroides por visitas + ticket descendente. El cluster con mayor suma siempre queda como 0 (VIP), garantizando etiquetas consistentes entre diferentes ejecuciones.
T5 Modelado supervisado — Random Forest — aprender las reglas de clasificación
services/mesero_randomforest_service.py · línea 14
# labels_remap = salida de K-Means → úsala como variable objetivo (y)
rf = RandomForestClassifier(
  n_estimators=200, # 200 árboles en el bosque
  max_depth=3, # profundidad máxima (evita sobreajuste)
  random_state=42, # reproducibilidad
  oob_score=True # validación Out-Of-Bag sin conjunto de prueba
)
rf.fit(X_arbol, labels_remap) # X: (n_mesas, 3), y: [0,1,2,...]

# Árbol representativo: el más cercano al promedio de importancias
imp_mean = rf.feature_importances_
diffs = [float(np.sum((t.feature_importances_ - imp_mean)**2)) for t in rf.estimators_]
arbol_rep = rf.estimators_[int(np.argmin(diffs))]
El Random Forest aprende las etiquetas que generó K-Means (pipeline híbrido no supervisado → supervisado). El árbol representativo se selecciona por mínima distancia al promedio de importancias, no el de mayor accuracy — así las reglas que se muestran son las más típicas del bosque.

L — Load

Carga — el resultado como JSON al cliente

El resultado final no se guarda en ninguna base de datos. Se construye un objeto Python y se serializa como JSON directamente al navegador del mesero. Chart.js lo renderiza en tiempo real sin ninguna capa de caché intermedia.

Estructura de la respuesta

puntos Lista de mesas con cluster, coordenadas x/y, color y recomendación
resumen Estadísticas por cluster: count, ticket promedio, ingreso total
evaluacion Silhouette Score, Inercia, curva Elbow para k=1..5
arbol Feature importances, reglas del árbol representativo, OOB Score

¿Por qué no se persiste?

Los datos cambian con cada comanda nueva — persistir el resultado lo haría obsoleto casi de inmediato.
Con 8 mesas el pipeline tarda menos de 200ms — recalcular es más rápido que leer caché.
Sin estado almacenado no hay desincronización entre el modelo y los datos reales.

controllers/mesero/kmeans_controller.py · línea 16

Los otros 3 análisis

Además del pipeline K-Means + Random Forest, el sistema ejecuta tres análisis independientes, cada uno con su propio proceso ETL adaptado al objetivo de cada modelo.

Análisis 1

Pareto 80/20 — Rentabilidad de Platillos

Ver análisis

Identifica qué platillos generan el 80% de los ingresos. La regla de Pareto aplicada a un menú permite priorizar sugerencias: si el mesero recomienda activamente los platillos del top 20%, maximiza el ingreso por comanda sin necesidad de ampliar el menú.

E Extracción

Aggregate sobre ventas: desanida el array items con $unwind y agrupa por nombre de platillo sumando ingresos. Filtra por los últimos N días.

T Transformación

Ordena por ingreso descendente. Calcula el porcentaje acumulado con suma corrida. Marca cada platillo con es_pareto=True mientras el acumulado no supere el 80%.

L Carga

JSON con lista de platillos ordenada, cada uno con rank, ingreso, % individual y acumulado, bandera es_pareto. La curva de Pareto se construye en Chart.js con doble eje.

Núcleo del cálculo — acumulado y umbral 80%
services/analytics/pareto_service.py
pipeline = [
  { "$match": { "fecha": { "$gte": hace_n_dias } } },
  { "$unwind": "$items" }, # desanidar cada producto de cada venta
  { "$group": {
    "_id": "$items.nombre",
    "ingreso": { "$sum": "$items.subtotal" }
  } },
  { "$sort": { "ingreso": -1 } }
]

# Calcular acumulado y marcar umbral 80%
total_ing = sum(p["ingreso"] for p in platillos)
acum = 0
for p in platillos:
  acum += p["ingreso"]
  p["pct_acumulado"] = round(acum / total_ing * 100, 1)
  p["es_pareto"] = acum <= total_ing * 0.80
No se usa scikit-learn — es aritmética pura sobre los resultados del aggregate. El umbral del 80% es paramétrico: se puede ajustar sin reentrenar ningún modelo. Endpoint: GET /api/analytics/pareto?dias=90

Análisis 2

Reglas de Asociación — Market Basket (Apriori)

Ver análisis

Descubre qué platillos se piden juntos con mayor frecuencia aplicando el algoritmo Apriori. Cada venta se trata como una "canasta" de productos. El resultado son reglas del tipo "si piden X → también piden Y" con tres métricas de confiabilidad.

Soporte
Fracción de transacciones que contienen ambos platillos. soporte(A,B) = P(A ∩ B)
Confianza
Probabilidad de B dado A. conf(A→B) = P(A ∩ B) / P(A)
Lift
Cuánto más probable es la asociación vs. azar. lift = conf / P(B). Lift > 1 = real.
E Extracción

Lee ventas.items de los últimos N días. Cada documento de venta se convierte en una lista de nombres de platillos (una "transacción"). Las ventas con un solo ítem se descartan.

T Transformación

1. TransactionEncoder convierte las listas en una matriz binaria (1 si el platillo está en la venta, 0 si no).
2. apriori() calcula conjuntos frecuentes.
3. association_rules() genera las reglas.

L Carga

JSON con las reglas ordenadas por lift descendente. Cada regla incluye antecedente, consecuente, soporte, confianza, lift y una descripción legible. Se limita a top 20 para no saturar la vista.

Pipeline mlxtend — de transacciones a reglas
services/analytics/asociacion_service.py
# E: construir lista de transacciones desde ventas.items
transacciones = [
  list({ it["nombre"] for it in v["items"] })
  for v in ventas if len(v["items"]) >= 2
] # ventas con 2 o más productos distintos

# T1: codificar como matriz binaria (platillo x transacción)
te = TransactionEncoder()
te_arr = te.fit_transform(transacciones)
df = pd.DataFrame(te_arr, columns=te.columns_)

# T2: conjuntos frecuentes con soporte mínimo
freq = apriori(df, min_support=0.04, use_colnames=True)

# T3: generar reglas con confianza mínima, ordenar por lift
reglas = association_rules(freq, metric="confidence", min_threshold=0.25)
reglas = reglas.sort_values("lift", ascending=False).head(20)
Si no hay suficientes transacciones (<10) o ninguna regla supera los umbrales, el servicio devuelve un aviso explicativo en lugar de una lista vacía. Endpoint: GET /api/analytics/asociacion?soporte=0.04&confianza=0.25

Análisis 3

Predicción de Demanda — Gradient Boosting

Ver análisis

Proyecta la demanda diaria (número de pedidos) para los próximos días usando un modelo de Gradient Boosting entrenado sobre el historial de ventas. A diferencia de los análisis anteriores, aquí el modelo aprende de patrones temporales: día de semana, mes, temporada alta, y si es fin de semana.

E Extracción

Agrupa ventas por fecha (día), contando el número de pedidos por día. Genera una serie temporal diaria con hasta 90 días de historial. Días sin ventas se rellenan con 0 para no romper la continuidad.

T Transformación

Extrae 5 features de cada fecha: weekday (0-6), month (1-12), is_weekend, is_high_season (Dic-Feb), day_of_month. Entrena con todo menos los últimos 7 días (holdout de validación).

L Carga

JSON con predicciones por día (pedidos estimados, ingreso proyectado, día de semana), historial de los últimos 30 días para la gráfica, métricas del modelo (MAE, RMSE, R²) e ingredientes estimados del top 15 de platillos más vendidos.

Feature engineering + entrenamiento
services/analytics/prediccion_service.py
# T: construir features de cada fecha del historial
def _features(fecha):
  return [
    fecha.weekday(), # 0=Lun … 6=Dom
    fecha.month, # 1–12
    1 if fecha.weekday() >= 5 else 0, # is_weekend
    1 if fecha.month in (12,1,2) else 0, # is_high_season
    fecha.day, # día del mes
  ]

X = [_features(d) for d in fechas_hist]
y = [conteo_por_dia[d] for d in fechas_hist]

modelo = GradientBoostingRegressor(
  n_estimators=200, max_depth=3,
  learning_rate=0.05, subsample=0.8, random_state=42
)
modelo.fit(X[:-7], y[:-7]) # train sin los últimos 7 días
y_val = modelo.predict(X[-7:]) # validar en esos 7 días (holdout)
Métricas de evaluación
MAE
Error absoluto medio. "El modelo se equivoca en promedio X pedidos por día." MAE bajo = predicciones más precisas.
RMSE
Raíz del error cuadrático medio. Penaliza más los errores grandes. Útil para detectar días donde el modelo falla mucho.
R²
Coeficiente de determinación. R²=1 es perfecto, R²=0 equivale a predecir siempre la media, R²<0 el modelo es peor que la media.
Con pocos días de historial (menos de 30) el modelo tiene poca señal — las métricas serán malas y el servicio lo indica con un aviso. Endpoint: GET /api/analytics/prediccion?dias_historial=90&dias_futuro=7
